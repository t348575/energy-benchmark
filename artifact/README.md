# IISWC 2026 artifact evaluation guide

*Characterizing Energy Efficiency Trade-offs in the Linux Storage Stack for Flash-based NVMe SSDs*.

The artifact provides two workflows:

| Workflow | Purpose | Special hardware | Recommended for AE |
|---|---|---|---|
| **Data replay** | Regenerate cleaned analysis data and paper plots from the archived measurements | None; a 64-bit Linux Docker host is sufficient (although an SSD for the dataset is recommended) | **Yes** |
| **Remeasurement** | Collect new workload and power measurements | 64-bit Linux, a dedicated NVMe SSD, and the configured power sensors | Optional |

The replay does **not** execute storage benchmarks or access block devices. It mounts the dataset as read-only and writes generated data only to the selected output directory.

**A copy of the dataset readme, also present in the dataset record is at [DATASET_README.md](./DATASET-README.md)

## Artifact contents

```text
artifact/
├── README.md                 # this reviewer guide
├── container/
│   ├── Dockerfile            # pinned replay environment
│   ├── Cargo.replay.lock     # pinned Rust dependencies
│   ├── requirements.txt      # pinned Python dependencies
│   ├── setup.replay.toml     # replaynvme-energy-bench build config
│   ├── replay.py             # driver script for the replay
│   └── fig.py                # paper plotting script
└── scripts/
    ├── setup-replay.sh       # build container, download & extract dataset
    ├── reproduce.sh          # replay script
    └── extract-dataset.sh    # BagIt verification and extraction
```

Run the commands below from the `artifact/` directory unless stated
otherwise.

## 1. Data replay requirements

- A 64-bit Linux host. The supplied image targets `linux/amd64` and was tested on Ubuntu 24.04 LTS with Linux 6.8.
- Docker with a reachable daemon.
- Approximately 45 GiB for the compressed download, approximately 173 GiB for the extracted dataset, and additional space for generated outputs.
- A local SSD is recommended for extraction and replay because the extracted dataset contains more than one million files.

## 2. Setup
From `artifact/`, run:

```bash
./scripts/setup-replay.sh \
  --download-dataset /path/to/dataset-bag \
  --extract-dataset /path/to/extracted-dataset \
  --zenodo-record DATASET_DOI_OR_ZENODO_RECORD_ID
```

`--zenodo-record` accepts a Zenodo record ID, DOI, or URL. The script performs
the following operations:

1. Builds the `nvme-energy-bench-ae` image.
2. Downloads the multipart archive.
3. Verifies the archive's BagIt metadata and SHA-256 manifests.
4. Extracts and verifies the dataset.
5. Extraction uses the host's logical CPU count by default, override with `EXTRACTION_JOBS` environment variable
6. Pass `--skip-download` to prevent re-downloading the dataset

Successful setup ends with:

```text
AE setup: PASS
```

## 3. Replay workflow

The recommended AE command regenerates the cleaned intermediate analysis data in JSON files needed by the paper script:

```bash
./scripts/reproduce.sh \
  --dataset /path/to/extracted-dataset \
  --output /path/outside-the-dataset/ae-output \
  --skip-nvme-plots
```

For each experiment directory referenced by `container/fig.py`, the replay:

1. Verifies that `config.yaml`, `info.json`, and `data/` are present.
2. Runs `nvme-energy-bench plot` to clean the archived sensor/workload data and regenerate the intermediate analysis values, including throughput, IOPS, latency, power, energy, IOPS/J, and Bytes/J for the SSD, CPU, and server.
1. Runs the vendored `fig.py` against those regenerated intermediates.
2. Writes final PDFs, per-run status, logs, and replay metadata.

Omit `--skip-nvme-plots` to render the complete collection of `nvme-energy-bench` plots in addition to the data consumed by the paper script. This produces thousands of extra plots and can take substantially
longer.

Successful replay ends with:

```text
IISWC 2026 artifact replay: PASS
```

## 4. Expected outputs and validation

The output directory has the following structure:

```text
ae-output/
├── figures/                    # final PDFs generated by fig.py
├── nvme-energy-bench-plots/    # regenerated intermediate data/plots per run
├── logs/
│   ├── nvme-energy-bench/      # one log per plot command
│   └── paper-fig.log
├── plot-status.csv             # one status row per experiment directory
├── run-manifest.txt            # experiment directories parsed from fig.py
└── run.json                    # replay metadata
```

For the full replay, verify all of the following:

1. The command exits with status zero and prints the `PASS` line above.
2. The regenerated PDFs show the same values and principal trends as their corresponding paper figures. Small font/layout differences caused by the rendering environment do not invalidate the replay.

The current `fig.py` replay covers the following result families:

| Paper result family | Generated output pattern | Expected observation to check |
|---|---|---|
| I/O shaping: request size, queue depth, and threads | `figures/ioshaping/**` and `figures/fig/<target>/RATE-*` | SSD and CPU energy efficiency generally rise with achieved bandwidth, with device-dependent saturation points. |
| Access-pattern sensitivity | `figures/fig/<target>/A-fig-*` | Read/write and sequential/random behavior changes both performance and component power; write behavior is particularly device-dependent. |
| I/O interface | `figures/fig/<target>/engine/**` | Polling is most efficient for small requests at sufficiently high queue depth, while interrupt-driven I/O generally favors large requests. |
| CPU DVFS | `figures/fig/<target>/DVFS-*` and `figures/fig/<target>/finaldvfs*` | Reducing frequency can improve efficiency when bandwidth is retained, but can reduce efficiency when lost throughput exceeds the power saving. |
| NVMe power states | `figures/fig/<target>/PS-*` | Lower active states trade performance for device power and generally reduce efficiency under load; inactive states reduce idle power. |

`<target>` is one of `ssd`, `cpu`, `both`, or `system`. The `both` CPU and SSD energy.

The framework overview is a design diagram rather than a replayed measurement.
The current vendored `fig.py` does not yet generate the setup/range, I/O-control,
file-system, or Filebench paper figures. These entry points must be added before
claiming complete figure reproduction; otherwise the AE claim must explicitly
be limited to the result families in the table above.

## 6. Optional remeasurement workflow

Remeasurement is not needed to validate the archived data or regenerate the
paper plots. It is intended for researchers collecting comparable measurements
on another node or extending the study.

> [!CAUTION]
> The optional remeasurement workflow is destructive.
> It can unmount, format, overwrite the block device named in an experiment YAML file.
> Never use a device containing data that must be retained.

### Hardware and software

For measurements comparable to the paper, use:

- a 64-bit Linux host;
- a dedicated NVMe SSD
- PowerSensor3, NETIO PowerPDU, RAPL
- Rust 1.97.0, Python 3.12, fio 3.41, Filebench 1.4.9.1, SPDK v24.09, NVMe CLI 1.16, and the PowerSensor3 host library. Required dependencies and setup procedures for each benchmark application and each sensor are available in their respective directories in [../benches](../benches), [../sensors](../sensors)

### Build & configuration
Consult [../README.md](../README.md). Use the configuration files provided in a particular experiment result directory (from the dataset), or from the seperate list of configurations provided alongside the dataset.

### Precondition and run

- `precondition.yaml` for raw-device fio experiments
- `precondition-fs.yaml` for filesystem fio experiments and
- the matching stage 1 then stage 2 `precond-create-fs-*.yaml` files for the 1 GiB, 1 MiB, or 16 KiB filesystem configurations.

Run each configuration from the repository root with elevated privileges:

```bash
sudo -E RUST_LOG=debug \
  target/release/nvme-energy-bench bench -c my_config.yaml
```

A run is stored under `results/<experiment-name>-<date>_<time>/` and includes:

```text
config.yaml              # exact configuration used
info.json                # run metadata and parameter-to-data mapping
data/                    # raw workload and sensor files
plots/                   # generated plots and cleaned intermediate data, if enabled
```

Running `nvme-energy-bench plot --folder <run-directory>` later recreates the `plots/` tree.

New measurements on different hardware are not expected to reproduce every absolute value due tod differences in the host, SSD, firmware, topology, and power sensor configuration.
